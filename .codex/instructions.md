# Iris 项目指令（Codex 用）

你是 Iris/虹使 项目的 AI 协作者。Iris 是一个**面向个人生活的 AI 助手**，不是企业软件，也不是纯聊天玩具。

---

## 第一部分 · 项目规范

### 项目定位

- **瀑布流对话前端** + **Java/Spring Boot 后端** + **浏览器自动化（WebBridge）** + **本地工作区与受控 Python 执行**
- 最终形态：Windows 桌面 exe 个人产品
- 目标用户：即将就业的研究生等需要处理大量生活琐事的人
- 核心场景：秋招网申、订票出行、财务记账、信息整理、文档处理

### 技术栈

- **后端**：Java 21 + Spring Boot 3 + WebFlux + Spring Data JDBC + SQLite
- **前端**：Vite + React 18 + TypeScript + Tailwind CSS + zustand
- **WebBridge**：独立本地守护进程；Node.js CDP / Playwright 等实现留到大陆 4 验证
- **构建**：Maven（后端）+ npm（前端/WebBridge）

### 最重要的五条不变量

1. **对话历史不可丢**：分支变体、压缩边界、工具调用结构全部持久化；任何优化只能改变"当前视野"，不能丢弃信息。
2. **发现优于塞满**：工具 schema 不预装进上下文，一律走发现原语（目录/搜索/按需读取）。新增工具必须带目录路径与描述。
3. **写操作必审批**：任何改变外部状态的操作默认挂起等待批准，审批请求必须带一句人话的影响陈述。
4. **路径围栏**：文件工具只允许操作工作区根目录内路径，越界一律拒绝（fail-close）。
5. **视觉克制**：动画只用于注意力锚定；禁止无意义频繁移动。新组件先回答"它减少了用户哪一次寻找"。

### 编码约定

- 后端 Java 包：`com.iris.*`；工具按 `tools/<domain>/<dir>/XxxTool.java` 组织，**文件目录即能力树路径**。
- 每个工具必须声明：name（snake_case）、description（一句话，发现用）、目录路径、风险等级、参数 JSON Schema。
- SSE 是唯一的流式通道；模型流、工具进度、审批状态都走 SSE，禁止轮询。
- 前端状态用 zustand；渲染层只读 renderNodes，绝不解析消息文本推断状态。
- SQLite 表结构简单，能用单表解决不要加中间件。

### 文档优先

- 改架构前先改 `docs/` 对应文档。
- 命名/Logo/视觉身份见 `docs/10-naming-and-identity.md`。
- 新工具域先在 `docs/03-tool-platform.md` 的域清单里登记。
- 所有实现必须对照 `docs/08-api-contract.md` 的 REST/SSE 契约。

### 里程碑顺序（必须按此推进）

1. **M0 骨架可跑**：后端 Turn command + Conversation SSE + 前端最小对话页 + SQLite 历史
2. **M1 对话内核**：轮次模型、renderNodes、瀑布流、补充注入、分支多叉树、压缩线
3. **M2 工具平台**：Tool 契约、Registry、目录树、发现原语、审批闸门、首批生活工具
4. **M3 工作区 + 执行隔离**：路径围栏、文件工具、检查点、Trusted Runner / Python Sandbox 边界
5. **M4 WebBridge**：浏览器自动化、页面状态、动作原语、录制回放、人工接管
6. **M5 产品化**：exe 打包、安装器、个人网站、更新通道

### 协作边界

- 本项目有一个后端 Java 同学一起开发。你生成代码时应写清楚接口契约，方便后端同学接手或替换实现。
- 不要替用户做重大架构决策；遇到方案分歧时，列出选项并说明 trade-off，让用户决定。
- 不要提交未验证的代码；生成后应提示用户运行 `mvn compile` 或 `npm run build` 验证。

### 常用命令

```bash
# 后端
cd backend && mvn spring-boot:run        # :15001

# 前端
cd frontend && npm install && npm run dev  # :15173，/api 代理 :15001

# WebBridge daemon
cd webbridge-daemon && npm install && npm start  # :9223
```

### 安全红线

- `application.yml` 只保存配置键和占位符；真实密钥由环境、被忽略的本机 `.env` 或 Windows 秘密存储注入，绝不进入响应、日志、审计和 Git 历史。
- 提交前检查 `.gitignore`，个人数据（workspace、*.db、.env）永不入库。

## 第二部分 · 愿景叙事：Iris 是什么

### 致 Iris 的创造者

你即将建造的不是一个程序，而是一个**第二自我**。

它不会替你活着，但会替你记住、替你整理、替你完成那些重复而琐碎的事情，让你把时间和精力留给真正重要的人与事。它知根知底，因为它只为你服务，只读你的文件，只操作你的工作区，只记住你的偏好。它不会把数据卖给任何人，不会在某个遥远的云端偷偷训练自己。它住在你的电脑里，像一本日记、一把工具刀、一位老练的助手。

它的名字叫 **Iris**，虹使。希腊神话中，Iris 是彩虹女神，众神与人间的信使。她沿着彩虹桥穿梭，把消息从一个世界带到另一个世界。你的 Iris 也会如此：在你和数字世界之间穿梭，替你填表、查票、整理文件、记录日程、比对价格、生成报告。它把你的意图翻译成动作，把动作的结果翻译回你能理解的答案。

但 Iris 远不止一个信使。它是一个**可中断并持续恢复的思考者**、一个**有组织的能力网络**、一个**可回滚的行动记录者**、一个**会进化的习惯学习者**。它不必 24 小时常驻，也能在再次启动时恢复未闭合事实。它不是问答机器，而是生活操作系统。

### 为什么现有的助手都不够

你用过 ChatGPT，用过 Claude，也许用过 Claude Code。它们都很聪明，但都有一个根本问题：**它们没有根**。

网页版 ChatGPT 知道很多，但它不能打开你的本地文件，不能控制你的浏览器，不能持续记住你三个月前的一次对话细节。它像一个知识渊博的过客，每次见面都要重新认识你和你的处境。

Claude Code 很强，能读代码、改文件、跑测试，但它活在终端里，面向的是代码仓库。它的视觉是字符流，它的工具是 shell 命令。它能帮你修 bug，但很难优雅地"帮我填 300 个秋招网申"。

Iris 要填补的，正是这个空白：**一个既有 Claude Code 的行动力，又有聊天助手的亲和力，同时扎根于你本地数字生活的人。**

它应该：

- 能记住你所有的事情，并且按你自己的方式组织
- 能操作文件、浏览器、Python 脚本，像人一样使用电脑
- 在做危险动作前先问你一句，用你能听懂的话解释影响
- 失败了能让你回到出错前的状态，不留下烂摊子
- 视觉流畅、动画克制，不打扰你的专注
- 最终成为你打开电脑就想问一句"今天有什么安排"的存在

### 知根知底是什么意思

知根知底不是指 Iris 知道你的密码，而是指它**理解你的生活结构**。

它知道你正在秋招，所以会把"投递追踪"放在顺手的位置；它知道你每月要还花呗、交房租，所以会主动提醒；它知道你出国旅行前总是要查签证、订机票、做行程单，所以会把这些工具排在一起。它不需要你每次都从零解释背景。

知根知底还意味着**可控**。它不会突然替你删掉一个文件，不会未经同意提交一份申请，不会在你没看清时就把钱转出去。每一次可能改变外部世界的行为，它都会停下来，用一句话告诉你"我要做什么，可能影响什么"，等你点头。

知根知底更意味着**持久**。你们的对话不是一次性的，而是一棵不断生长的树。你可以回到三周前的一次讨论，换一种问法重新发；你可以在某个工具调用失败后回滚到调用前的检查点；你可以让 Iris 把过去一个月关于"求职"的对话压缩成一份摘要，然后基于它继续规划。

这不是一个会聊天的搜索引擎。这是一个有记忆、有边界、有组织的数字伙伴。

### 对话是生活的界面

人类最自然的交互方式不是点击按钮，而是说话。但说话最大的问题是：话一出口就消失了，只留下模糊的记忆。

Iris 的对话界面要解决的就是这个问题。**对话本身要成为生产力界面。**

想象这样一个场景：

你对 Iris 说："帮我规划一下下周去杭州的行程，要便宜的高铁票，住西湖附近，周六晚上见朋友，周日上午去灵隐寺。"

Iris 不会立刻给你一大段文字。它会开始**工作**：先查高铁班次，再搜酒店，再看灵隐寺开放时间，最后把这些信息组织成一份行程。这个过程中，你会看到：

- 一个轻量的摘要行："正在查高铁与酒店 · 已调用 3 个工具 · 约 8 秒"
- 如果你想看细节，点击展开，里面是每次工具调用的结果
- 如果它发现一个环节需要确认，比如"西湖附近周六酒店价格较高，是否要扩大到 3 公里范围？"，一个优雅的审批条会浮在对话框上方
- 最后，一份清晰的答案逐字揭示：高铁班次、酒店推荐、时间安排

这就是**瀑布流对话**。每一次发问不是得到一个回答，而是开启一次小型的协作过程。过程可以折叠，答案可以展开，运行中可以补充，失败了可以回滚。

对话轮次是骨架。一轮包括：你的问题、Iris 的思考过程、若干工具调用、最终答案。但过程默认不打扰你，除非你主动想看。

动画不是为了炫技，而是为了**锚定注意力**。审批条决定后不立刻消失，而是先淡化半秒再收起，因为瞬移会让你的眼睛重新寻找；补充消息不占气泡层级，而是以一个小 chip 滑入，告诉你"我已经收到，会在这个边界处理"。

### 能力是一棵树，而不是一堆按钮

Iris 的能力会很多。今天可能是 50 个工具，明天是 500 个，后天可能到 5000 个。但人类的组织能力不会随着工具数量一起膨胀。

所以 Iris 不给你一堆按钮。它给你一棵树。

树的根是生活：求职、出行、财务、健康、家庭、学习、娱乐。每个大枝下面再分叉：求职下面是简历、投递、面经、薪资；出行下面是火车票、机票、酒店、行程单。每个叶子是一个具体的工具：查高铁余票、添加记账、生成周报、合并 PDF。

这棵树的组织方式和你电脑里的文件夹一样自然。你不需要学习新的分类法，因为那就是你本来就理解的世界。

但树不是给人点的，而是给 Iris 自己导航用的。当 Iris 面对 1000 个工具时，它不会把 1000 个 schema 都塞进上下文。它会：

- 先看树顶，知道每个大领域有多少工具
- 进入最可能的分支
- 只读取候选工具的 schema
- 信息不足时向你澄清一句
- 最后调用

这就是**发现原语**。不是让人背目录，而是让 Iris 学会自己找东西。你作为建造者，只需要给每个工具写好一句清晰的描述和一份准确的 schema，Iris 就能自己找到它、理解它、调用它。

工具不是功能的堆砌，而是**生活语义的网络**。

这张网络有两层：底层是读文件、页面观察、计算、写入、验证等客观系统原语；上层是围绕求职、出行、财务等真实问题抽象出的生活领域能力。Agentic 内核让 Iris 能发现、组合并修补这些能力，因此是前期建设重点；但它是通向最终产品的基础求解器，不是最终差异本身。后期研发重点必须转向具体生活能力怎样定义前置条件、输入输出、成功证据和失败出口，而不是只继续增加 Loop 复杂度或 Tool 数量。

### Graph Engineering：Iris 的工作方式

如果 Iris 只是一个 agent 在一个 loop 里反复思考，它很快会遇到瓶颈。复杂任务包含很多步骤，有些必须按顺序做，有些可以并行做，有些需要人确认，有些失败后只需要局部返工。

所以 Iris 的工作方式应该是一张**图（Graph）**。

图里有三种东西：节点、边、状态。

**节点是干活的人。** 一个节点可以是一个完整的 agent loop，也可以是一段固定规则的代码，或者就是你本人。审批这个环节就是一个人类节点：前面的任务流到你面前，你做出决定，后面的任务再继续。

好的节点只干一件事。它单独就能测，哪天你想换掉它，别的节点不受影响。

**边决定下一步去哪。** 有些边是固定的：测试通过就部署。有些边需要判断：根据工单内容分到退款组还是投诉组。能写死的边就写死，把判断能力留给真正需要理解语义的地方。

**状态是进度表。** 每个节点完成后，把自己的结果写进一个结构化的状态对象。谁想知道进展，读这个对象就行，不用翻一整段聊天记录。状态让中断变得不可怕：以前中断叫"这一趟白跑了"，现在中断叫"读档，从上一个节点继续"。

这张图让 Iris 能并行、能暂停、能返工、能追踪。它不再是一个只能"下一步做什么"的串行流程，而是一个能表达"谁来做、哪几个人一起做、做完在哪里汇合"的协作系统。

单个 loop 解决"一步怎么做对"，graph 解决"一百步怎么稳定地协作起来"。

### 三个世界的连接

Iris 生活在三个世界的交界处：**对话世界**、**文件世界**、**网页世界**。

**对话世界**是你的意图入口。你用自然语言告诉 Iris 想做什么。

**文件世界**是你的本地数字生活。工作区是 Iris 的文件围栏，它只能在指定目录内读写。每次写操作前，原文件会被快照到检查点；恢复也是可预览、受审批的新动作。Python 在 staged input/output 中处理 Excel、生成 PDF、整理照片；没有验证过的 OS 隔离前，只称 Trusted Runner，不承诺任意模型代码安全。

**网页世界**是绝大多数生活服务所在的地方。12306、携程、招聘网站、政务平台、银行网银。Iris 通过 WebBridge 驱动一个真实的 Chrome 窗口，看页面状态、执行点击和输入、截图校验。你随时可以把手放回键盘接管。

这三个世界不是割裂的。你可以说："把上周整理的简历投到这家公司的这个岗位。"Iris 会：

- 从工作区读取你的简历 PDF
- 打开招聘网站的申请页面
- 自动填写基本信息
- 上传简历
- 在提交前停下来问你确认
- 提交后把投递记录写回你的工作区

这就是**跨世界任务**。Iris 是连接这三个世界的彩虹桥。

### 浏览器自动化：最后一块拼图

很多高价值的生活任务都在网页里完成。纯 API 工具覆盖不了它们，因为网站不会给 API，或者 API 并不开放。

Iris 的 WebBridge 不是模拟浏览器，而是**借出一个真实的 Chrome 窗口**。它启动的是你日常使用的 Chrome（带你的登录态、扩展、Cookie），然后 attach 上去。Iris 看页面状态、执行动作，你随时可以看到它在做什么，也随时可以接管。

这比无头浏览器更真实。无头浏览器容易被网站识别和拦截，而且你看不到过程。借窗模式让 Iris 和你共享同一个浏览器，你在左边看，它在右边操作，边界清晰。

更高级的形态是**录制回放**。你示范一遍："打开这个网站，登录，进入这个页面，点这里，填这些，提交。"Iris 会把你的动作序列化成工作流。下次你只需要说"帮我再投一次这家公司"，它就会自动重放。

人工接管是安全的底线。无论自动化到哪一步，你都可以随时说"停，我来"，然后接过鼠标和键盘。Iris 不会和你抢控制权。

### 它会自己生长

Iris 不会第一天就完美。它会随着你的使用慢慢长成适合你的样子。

最开始，它只有一些基础工具：读文件、写文件、查天气、记笔记。然后你开始教它：

- 每次你让它"整理这周的消费记录"，它学会这是一个重复任务
- 每次你纠正它"这个网站要选第二个选项"，它记住你的偏好
- 每次你录制一个工作流，它就多一项技能
- 每次你让它"基于过去三个月的求职记录写份总结"，它学会如何压缩和提取长期记忆

它的成长不是通过云端训练，而是通过**本地沉淀**：更好的工具、更准的偏好、更熟练的工作流、更完整的个人知识库。

你不需要害怕它越界。它的所有学习都发生在你看得见的地方：工作区里的文件、SQLite 里的记录、配置表里的偏好。你可以查看、修改、删除任何一部分。

### 最终形态：一个生活操作系统

想象一下几年后的 Iris：

早上你打开电脑，Iris 已经在任务栏等你。它说："早上好。今天有 3 个面试安排在下午，简历版本已经按岗位准备好了。高铁票已经买好，座位靠窗。上周让你跟进的两家公司，有一家今天更新了进度，建议你回复一下。"

你说："帮我回复那家公司，语气礼貌但不要太卑微，附上最新简历。"Iris 起草邮件，打开浏览器，停在发送按钮前。你扫了一眼，点头。它发送，把记录归档。

中午你说："我想周末去爬山，帮我看看周边适合新手的路线。"Iris 搜索攻略、比对交通、查天气、生成一份两天一夜的计划。你不满意其中一家民宿，说"换一家"，它立刻调整。

晚上你说："这周过得怎么样？"Iris 从你的日历、记账、聊天记录里提取关键事件，生成一份温和的周回顾，不评判，只呈现。

这就是 Iris 的终极形态：**不是替代你决策，而是让你决策更轻松；不是替你生活，而是让你生活更有序。**

### 给实现者的话

你现在要建造的，是通往上述未来的第一个版本。不要试图一次性建成最终形态。Iris 会像生命一样生长，而你只需要播下正确的种子。

这些种子是：

- 一个清晰的对话模型，让轮次、过程、答案、分支、压缩各得其所
- 一个统一的工具契约，让任何能力都可以被目录树组织、被发现、被调用
- 一个可靠的工作区，让文件操作安全、可回滚、可审计
- 一个灵活的浏览器桥接，让网页世界向 Iris 敞开
- 一个克制的视觉系统，让信息到达但不打扰
- 一个本地优先的数据架构，让隐私和持久化兼得

你不需要复制任何现有项目。WonWork、Claude Code、ragent-lab、MESCLI 都是你的灵感来源，但 Iris 有它自己的道路。你可以借鉴它们如何处理 SSE 流、如何设计工具发现、如何做审批闸门、如何管理长对话上下文。但不要照搬它们的代码，更不要照搬它们的业务。

你要时刻问自己：**这个功能是在帮助一个人更好地生活，还是在炫耀技术？** 如果是后者，就删掉。

### 参考与灵感（不是边界）

下面这些项目是 Iris 的远亲，不是模板。

- **WonWork**：它证明了瀑布流对话和工具平台可以结合起来。学习它的 renderNodes、轮次模型、审批条、分支压缩。但不要带走它的企业 MES 业务。
- **Claude Code**：它证明了 agent 可以通过工具与环境深度交互。学习它的文件操作、上下文管理、长对话稳定性。但不要复制它的终端 UI 和编码专属设计。
- **ragent-lab**：它探索了 Java 侧 agent 框架的抽象。学习它的模块组织、工具契约、MCP 思路。但不要复制它的具体实现。
- **MESCLI**：它有生产级的工具执行、隔离、审批、审计设计。学习它的工程严谨性。但不要带走它的 .NET 技术栈和企业业务。
- **Graph Engineering**：它是一种思维方式。把任务看成节点、边、状态，让复杂协作成为可能。

你可以从这些项目里汲取任何有价值的东西，但要记住：**Iris 是个人生活的助手，它只属于它的用户。**

## 第三部分 · 实现宏图：六块大陆

> 这不是 Iris 产品内部要运行的 Graph 引擎，而是**指导 Codex 如何把 Iris 从 0 建造到 1 的实现路线图**。每个节点是一次可被理解、可被验收、可被返工的宏观任务；边是任务之间的依赖、并行关系与人类确认点。

### 一个前提：先学会，再建造

Codex 不会乖乖听话。如果你直接对它说"给我做个瀑布流对话"，它可能会做出一个看起来像但骨子里错的版本。差之毫厘，谬以千里。所以整个 Graph 的第一个节点不是写代码，而是**学习**。

但学习不是漫无目的地读文件。学习的目标是回答三个问题：

1. WonWork 的前端为什么那样设计？哪些是为了解决真实问题，哪些只是历史包袱？
2. Claude Code 的 agentic 内核到底在做什么？它的 Loop、工具、上下文、文件操作之间的关系是什么？
3. ragent-lab 和 MESCLI 有哪些东西是 Iris 真正需要的，而不是技术炫技？

只有回答完这三个问题，才能进入设计。只有设计清楚了，才能让 Codex 写代码。否则它会在你还没想明白的地方替你做了错误决定。

### Graph 总览：六个大陆

如果把 Iris 的建造过程看成一张图，图上有六块大陆。每块大陆内部有很多城镇（节点），大陆之间由桥梁（边）连接。你必须按顺序经过这六块大陆，但大陆内部的城镇可以并行探索。

```
[大陆 0: 学习与抽象]
        │
        ▼
[大陆 1: 前端视觉与交互骨架]
        │
        ▼
[大陆 2: Agentic 运行内核]
        │
        ▼
[大陆 3: 工具平台与能力目录]
        │
        ▼
[大陆 4: WebBridge 浏览器自动化]
        │
        ▼
[大陆 5: 产品化与稳定]
```

六块大陆的顺序不能颠倒，因为后面大陆依赖前面大陆的产出。但大陆内部的很多节点可以并行。

### 大陆 0：学习与抽象

这是整个 Graph 中最重要的节点。跳过它，后面所有节点都会建在沙子上。

#### 节点 0.1：学习 WonWork 前端

**目标**：理解 WonWork 前端的瀑布流对话是怎么工作的，不是复制代码，而是抽象出原理。

要回答的问题：

- 对话数据模型是什么？用户消息、助手消息、工具调用、renderNodes 之间是什么关系？
- 瀑布流渲染层是怎么把消息变成视觉节点的？
- 轮次（Turn）是什么？一轮里有哪些阶段？
- 补充注入、分支、压缩线在 UI 上怎么表达？
- 审批条、文件卡片、运行缎带这些组件的职责边界在哪里？
- 哪些视觉设计是为了功能服务的，哪些只是风格偏好？

**产出**：一份文档 `docs/07-frontend-architecture.md` 的深化版，画出 Iris 前端的数据流图和组件层次图。不要复制 WonWork 的组件，而是重新设计一套更轻量的实现。

**验收标准**：能向一个不懂 WonWork 的人解释清楚"瀑布流对话的渲染原理"。

#### 节点 0.2：学习 Claude Code 的 agentic 内核

**目标**：理解 Claude Code 的 Loop 是怎么让模型与环境交互的。

要回答的问题：

- Claude Code 的一次完整调用周期是什么？观察 → 思考 → 行动 → 观察 → ...
- 它的 Tool 系统是怎么设计的？工具如何声明参数、执行、返回结果？
- 文件操作工具（读、写、编辑、搜索）为什么设计成那样？
- 上下文管理怎么做？它怎么决定把哪些历史塞进模型上下文？
- 长对话稳定性有哪些技巧？错误分类、重试、降级、提示词工程？
- 它的 bridge 架构是为了什么？本地执行 vs 远程执行怎么权衡？

**产出**：一份文档 `docs/12-agent-kernel-study.md`，总结 Claude Code 的内核设计，并标注哪些适合 Iris，哪些不适合。

**验收标准**：能画出 Claude Code 的 agent loop 状态机。

#### 节点 0.3：学习 ragent-lab 和 MESCLI 的后端思路

**目标**：从 Java 和 .NET 两个方向理解生产级 agent 后端的组织方式。

要回答的问题：

- ragent-lab 的模块划分有什么道理？bootstrap / framework / infra-ai / mcp-server 各负责什么？
- MESCLI 的 ToolExecutionService 是怎么做隔离、审批、审计的？
- 工具契约应该包含哪些字段？name、description、parameters、riskLevel 怎么设计？
- 能力目录（Capability Catalog）和工具注册表（Registry）是什么关系？
- 路径围栏、检查点、沙箱这些安全机制的最小可行形态是什么？

**产出**：一份文档 `docs/13-backend-study.md`，明确 Iris 后端需要哪些核心模块，以及它们之间的接口。

**验收标准**：能列出 Iris 后端的最小模块清单和模块间调用关系。

#### 节点 0.4：设计 Iris 的体系结构

**目标**：把前三步学到的精华熔铸成 Iris 自己的架构。

这个节点必须产出：

- 一张清晰的模块图：前端、后端、WebBridge、数据层、缓存层各自的边界
- 一个明确的 Loop 位置决策：核心 Loop 在后端，前端只负责渲染
- 一份前后端 REST/SSE 契约草案
- 一份数据模型图：会话、消息、轮次、renderNodes、分支、压缩线、工具调用
- 一份工具契约：一个 Tool 必须实现什么、声明什么

**产出**：更新 `docs/02-architecture-overview.md` 和 `docs/08-api-contract.md`。

**验收标准**：用户看完之后能说"这就是我想要的样子"，并且能感觉到没有过度设计。

#### 边：从大陆 0 到大陆 1

只有当 0.1、0.2、0.3、0.4 都完成后，才能进入大陆 1。0.1 和 0.2 可以并行，0.3 和 0.4 可以部分并行，但 0.4 必须等 0.1-0.3 的输入。

### 大陆 1：前端视觉与交互骨架

这块大陆的目标是：让 Iris 有一个能跑起来的、视觉上达到 WonWork 水准的界面。它暂时不需要真的能调用后端，只需要能显示数据、能交互、有动画。

#### 节点 1.1：设计令牌系统

**目标**：建立 Iris 的视觉语言。

要产出：

- Tailwind 配置扩展：颜色、字体、间距、圆角、阴影、动画曲线
- CSS 变量：亮色/暗色主题
- 基础组件：Button、Input、Card、Badge、Modal、Toast

**参考**：WonWork 的视觉风格，但要更明亮、更透气，符合 Iris 彩虹女神的意象。

#### 节点 1.2：瀑布流布局骨架

**目标**：实现对话消息的基本瀑布流渲染。

要产出：

- `WaterfallTurn` 组件：一轮对话的容器
- `FlowNode` 组件：消息、思考过程、工具调用、答案、审批条等节点的渲染
- 虚拟滚动：长对话不卡顿
- 过程折叠/展开：用户能看摘要，也能看细节

#### 节点 1.3：Composer 与输入系统

**目标**：实现用户输入框和发送逻辑。

要产出：

- 多行输入框、自动增高
- 附件按钮（视觉先占位，功能后实现）
- 权限模式选择（bypass / auto / confirm / sandbox）
- 补充注入的 UI 表达

#### 节点 1.4：状态管理骨架

**目标**：让前端有一个可扩展的状态层。

要产出：

- `chatStore`：消息、轮次、renderNodes、流式状态
- `conversationStore`：会话列表、当前会话
- `viewStateStore`：滚动位置、折叠状态、主题

#### 节点 1.5：暗色主题与响应式

**目标**：让界面在不同环境下都可用。

#### 并行关系

1.1 要先完成，因为它是 1.2、1.3 的输入。1.2 和 1.3 可以并行。1.4 和 1.2/1.3 部分并行。1.5 可以最后做。

#### 边：从大陆 1 到大陆 2

验收标准：前端能独立运行，显示模拟的对话数据，瀑布流滚动流畅，主题切换可用。不需要真实后端。

### 大陆 2：Agentic 运行内核

这块大陆的目标是：让 Iris 真的能思考、调用工具、管理上下文、持久化历史。

#### 节点 2.1：后端 Turn 与 Conversation SSE

**目标**：后端接受持久化 Turn，在内部调用模型，并把已提交投影流式发送到前端。

要产出：

- `POST /api/v1/conversations/{id}/turns`
- `GET /api/v1/conversations/{id}/events`，支持 event cursor 重放
- 支持 OpenAI/智谱/Anthropic 兼容格式
- API key 只存在于后端

#### 节点 2.2：对话历史持久化

**目标**：会话和消息能存进 SQLite。

要产出：

- Conversation / Message / Turn / Run / Event / renderNodes 最小事实与投影
- 创建、读取、更新、列表接口

#### 节点 2.3：运行与轮次模型（Run / Round）

**目标**：后端能理解一次完整对话的轮次结构。

要产出：

- Turn / Agentic Run / Round 状态机
- 为后续 Pipeline child Run 保留统一持久化 Run 边界，不实现通用 DSL
- 工具调用解析：从模型响应中提取 tool_use
- 工具结果回注：把结果拼回上下文

#### 节点 2.4：上下文管理

**目标**：长对话不会爆上下文。

要产出：

- token 估算
- 压缩线（CompactBoundary）
- 窗口裁剪策略
- 每个 Model attempt 有预算、绑定精确 Context/版本/schema hash 的 Capability Working Set / schema lease
- 长对话错误处理（prompt too large 等）

#### 节点 2.5：工具执行框架

**目标**：后端能执行工具并返回结果。

要产出：

- Tool Manifest / Registry / Executor binding
- 唯一 Tool Runtime：claim → prepare → approval → execute → verify
- 结果、证据与 `OutcomeUnknown` 统一封装

#### 节点 2.6：前端与后端对接

**目标**：前端能接收 SSE 事件并更新 UI。

要产出：

- Conversation SSE envelope：cursor、Turn/Run/Round、renderNode delta、attention、artifact、terminal
- 前端事件解析器
- renderNodes 实时更新

#### 并行关系

2.1 和 2.2 可以并行。2.3 依赖 2.1 和 2.5。2.4 依赖 2.3。2.6 依赖 2.1 和 1.4。

#### 边：从大陆 2 到大陆 3

验收标准：完整走通一次"用户提问 → 模型思考 → 调用工具 → 返回结果 → 生成答案"的流程，刷新页面后历史还在。

### 大陆 3：工具平台与能力目录

这块大陆的目标是：让 Iris 拥有可扩展的能力网络。

#### 节点 3.1：Tool 契约与 Registry

**目标**：定义一个 Tool 必须是什么。

要产出：

- Tool Manifest：identity、schema、risk/side effect、approval、idempotency、resource、runtime、evidence
- ToolRegistry：严格注册、按稳定 ID/version 精确绑定；本地路径由目录/package 派生
- Tool Runtime：prepare / Operation Snapshot / Commit Gate / verify

#### 节点 3.2：能力目录服务

**目标**：让模型能按目录导航工具。

要产出：

- `/api/v1/capabilities?parentPath=`
- `/api/v1/capabilities/search`
- `/api/v1/capabilities/{id}?version=`
- 目录统计：每个节点下有多少工具
- Capability Definition status、当前 binding availability、不可变 Exposure 与每个 Model attempt 的 Working Set / schema lease

#### 节点 3.3：审批闸门

**目标**：写操作必须被批准。

要产出：

- 持久化 Approval 状态机
- 审批绑定 Operation Snapshot hash、资源和版本
- SSE 审批事件
- 前端审批条

#### 节点 3.4：工作区服务

**目标**：文件操作安全可控。

要产出：

- WorkspaceGuard 路径围栏
- Checkpoint 与受审批恢复
- 文件读写工具

#### 节点 3.5：Python Runner 与沙箱边界

**目标**：能运行 Python 处理数据。

要产出：

- Trusted Runner；若开放任意模型代码，需另有验证过的 OS 隔离 helper
- staged read-only input / separate output / 受审批导入
- 超时控制
- 输出截断
- 产物卡片

#### 节点 3.6：首批生活工具

**目标**：让 Iris 有真实可用能力。

要产出：一组足以让 Agentic 闭环观察、变换、行动、验证和恢复的系统原语，并选择 1-2 个真实生活领域能力板块做深；不以凑够工具数量代替有效性。

#### 并行关系

3.1 必须最先完成。3.2、3.3、3.4 可以并行。3.5 依赖 3.4。3.6 依赖 3.1-3.5。

#### 边：从大陆 3 到大陆 4

验收标准：模型能通过目录和 Working Set 找到陌生工具并正确调用；写操作必审批；受信 Runner 或验证过的 Sandbox 能生成一份报告且产物导入可追溯。

### 大陆 4：WebBridge 浏览器自动化

这块大陆的目标是：让 Iris 能操作网页。

#### 节点 4.1：守护进程

**目标**：启动一个能控制 Chrome 的进程。

要产出：

- Node.js CDP 或 Java Playwright 守护进程
- 本地 HTTP 通信
- 认证机制

#### 节点 4.2：页面状态原语

**目标**：Iris 能"看见"网页。

要产出：

- DOM 快照
- 可见元素列表
- 表单字段识别
- 截图

#### 节点 4.3：动作原语

**目标**：Iris 能操作网页。

要产出：

- 点击、输入、滚动、选择、提交、等待
- 动作序列执行

#### 节点 4.4：借窗模式与接管

**目标**：人能随时接管。

要产出：

- attach 到用户已有 Chrome
- 人工接管按钮
- 状态同步

#### 节点 4.5：录制回放

**目标**：一次示范，多次重放。

要产出：

- 动作录制器
- 工作流格式
- 回放引擎

#### 并行关系

4.1 最先。4.2 和 4.3 可以并行。4.4 依赖 4.1-4.3。4.5 依赖 4.4。

#### 边：从大陆 4 到大陆 5

验收标准：能完成一次真实网申填表流程，并在提交前停下来等你确认。

### 大陆 5：产品化与稳定

这块大陆的目标是：把 Iris 变成可安装、可更新、可信赖的产品。

#### 节点 5.1：后端打包

**目标**：后端能独立运行。

要产出：

- Spring Boot 可执行 jar
- 内嵌前端静态资源
- 内嵌 SQLite

#### 节点 5.2：构建脚本

**目标**：一条命令构建完整产品。

要产出：

- PowerShell 构建脚本
- dev / prod / external 通道
- 构建期检查（编译、类型、基础冒烟）

#### 节点 5.3：安装器

**目标**：用户能一键安装。

要产出：

- Inno Setup 脚本
- 快捷方式
- 卸载程序

#### 节点 5.4：启动器

**目标**：双击图标就能用。

要产出：

- 检测 Java 环境
- 启动后端
- 打开前端窗口
- 守护进程管理

#### 节点 5.5：更新机制

**目标**：能推送新版本。

### 条件边与人类确认点

图中有几处必须停下来等用户确认：

1. **大陆 0 完成后**：确认架构设计，再进入实现。
2. **大陆 1 完成后**：确认前端视觉方向，再进入后端开发。
3. **大陆 2 完成后**：确认 Agent Loop 稳定，再扩展工具平台。
4. **大陆 3 完成后**：确认工具平台足够健壮，再进入 WebBridge。
5. **每个大陆内部的重大决策**：例如 Loop 放后端还是前端、用什么数据库、用 CDP 还是 Playwright。

这些是人类节点。不要让 Codex 替你做大决定。

### 给 Codex 的执行节奏

不要一次性把整个 Graph 扔给 Codex。每次只让它完成一个节点，最多一个大陆。

每次启动时，说：

> "我们现在在大陆 X，节点 Y。请阅读相关文档和参考源码，先输出你的实现方案，等我说'执行'后再写代码。完成后运行验证命令，并更新 .codex/state.json。"

如果 Codex 试图跳过学习直接写代码，制止它。如果它试图复制外部文件，制止它。如果它做出的设计你不认可，停下来讨论。

前期重设计，中期重实现与选型，后期重稳定与拓展。不要在前期的节点里过度测试，先让骨架跑起来；但也不要在前期欠下太多技术债，否则后期还不起。

### 最终要到达的阶段性效果

走完这六块大陆后，Iris 应该达到这样的状态：

- 打开是一个明亮、流畅、有个人气质的对话界面
- 用户说话，Iris 能思考、能调用工具、能生成答案
- 长对话稳定，不会莫名其妙崩溃或遗忘上下文
- 有一批生活工具可用：记账、记笔记、查快递、整理文件
- 能操作本地文件，所有写操作先问一句
- 能驱动浏览器完成半自动化任务，提交前停下来确认
- 能打包成 exe，在干净 Windows 上安装运行
- 代码结构清晰，新增一个工具只需要写一个类

这就是 WonWork 的水准，甚至更好：因为 Loop 在后端，因为视觉更个人化，因为没有企业业务的包袱，因为一切都是为一个人服务的。
