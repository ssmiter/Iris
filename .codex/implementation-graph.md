# Iris 实现宏图的 Graph

> 这不是 Iris 产品内部要运行的 Graph 引擎，而是**指导 Codex 如何把 Iris 从 0 建造到 1 的实现路线图**。每个节点是一次可被理解、可被验收、可被返工的宏观任务；边是任务之间的依赖、并行关系与人类确认点。

---

## 0. 一个前提：先学会，再建造

Codex 不会乖乖听话。如果你直接对它说"给我做个瀑布流对话"，它可能会做出一个看起来像但骨子里错的版本。差之毫厘，谬以千里。所以整个 Graph 的第一个节点不是写代码，而是**学习**。

但学习不是漫无目的地读文件。学习的目标是回答三个问题：

1. WonWork 的前端为什么那样设计？哪些是为了解决真实问题，哪些只是历史包袱？
2. Claude Code 的 agentic 内核到底在做什么？它的 Loop、工具、上下文、文件操作之间的关系是什么？
3. ragent-lab 和 MESCLI 有哪些东西是 Iris 真正需要的，而不是技术炫技？

只有回答完这三个问题，才能进入设计。只有设计清楚了，才能让 Codex 写代码。否则它会在你还没想明白的地方替你做了错误决定。

---

## 1. Graph 总览：六个大陆

如果把 Iris 的建造过程看成一张图，图上有六块大陆。每块大陆内部有很多城镇（节点），大陆之间由桥梁（边）连接。你必须按顺序经过这六块大陆，但大陆内部的城镇可以并行探索。

```
[大陆 0: 学习与抽象]
        │
        ▼
[大陆 1: 前端视觉与交互骨架]
        │
        ▼
[大陆 2: Agentic 运行内核]
        │
        ▼
[大陆 3: 工具平台与能力目录]
        │
        ▼
[大陆 4: WebBridge 浏览器自动化]
        │
        ▼
[大陆 5: 产品化与稳定]
```

六块大陆的顺序不能颠倒，因为后面大陆依赖前面大陆的产出。但大陆内部的很多节点可以并行。

---

## 2. 大陆 0：学习与抽象

这是整个 Graph 中最重要的节点。跳过它，后面所有节点都会建在沙子上。

### 节点 0.1：学习 WonWork 前端

**目标**：理解 WonWork 前端的瀑布流对话是怎么工作的，不是复制代码，而是抽象出原理。

要回答的问题：

- 对话数据模型是什么？用户消息、助手消息、工具调用、renderNodes 之间是什么关系？
- 瀑布流渲染层是怎么把消息变成视觉节点的？
- 轮次（Turn）是什么？一轮里有哪些阶段？
- 补充注入、分支、压缩线在 UI 上怎么表达？
- 审批条、文件卡片、运行缎带这些组件的职责边界在哪里？
- 哪些视觉设计是为了功能服务的，哪些只是风格偏好？

**产出**：一份文档 `docs/07-frontend-architecture.md` 的深化版，画出 Iris 前端的数据流图和组件层次图。不要复制 WonWork 的组件，而是重新设计一套更轻量的实现。

**验收标准**：能向一个不懂 WonWork 的人解释清楚"瀑布流对话的渲染原理"。

### 节点 0.2：学习 Claude Code 的 agentic 内核

**目标**：理解 Claude Code 的 Loop 是怎么让模型与环境交互的。

要回答的问题：

- Claude Code 的一次完整调用周期是什么？观察 → 思考 → 行动 → 观察 → ...
- 它的 Tool 系统是怎么设计的？工具如何声明参数、执行、返回结果？
- 文件操作工具（读、写、编辑、搜索）为什么设计成那样？
- 上下文管理怎么做？它怎么决定把哪些历史塞进模型上下文？
- 长对话稳定性有哪些技巧？错误分类、重试、降级、提示词工程？
- 它的 bridge 架构是为了什么？本地执行 vs 远程执行怎么权衡？

**产出**：一份文档 `docs/12-agent-kernel-study.md`，总结 Claude Code 的内核设计，并标注哪些适合 Iris，哪些不适合。

**验收标准**：能画出 Claude Code 的 agent loop 状态机。

### 节点 0.3：学习 ragent-lab 和 MESCLI 的后端思路

**目标**：从 Java 和 .NET 两个方向理解生产级 agent 后端的组织方式。

要回答的问题：

- ragent-lab 的模块划分有什么道理？bootstrap / framework / infra-ai / mcp-server 各负责什么？
- MESCLI 的 ToolExecutionService 是怎么做隔离、审批、审计的？
- 工具契约应该包含哪些字段？name、description、parameters、riskLevel 怎么设计？
- 能力目录（Capability Catalog）和工具注册表（Registry）是什么关系？
- 路径围栏、检查点、沙箱这些安全机制的最小可行形态是什么？

**产出**：一份文档 `docs/13-backend-study.md`，明确 Iris 后端需要哪些核心模块，以及它们之间的接口。

**验收标准**：能列出 Iris 后端的最小模块清单和模块间调用关系。

### 节点 0.4：设计 Iris 的体系结构

**目标**：把前三步学到的精华熔铸成 Iris 自己的架构。

这个节点必须产出：

- 一张清晰的模块图：前端、后端、WebBridge、数据层、缓存层各自的边界
- 一个明确的 Loop 位置决策：核心 Loop 在后端，前端只负责渲染
- 一份前后端 REST/SSE 契约草案
- 一份数据模型图：会话、消息、轮次、renderNodes、分支、压缩线、工具调用
- 一份工具契约：一个 Tool 必须实现什么、声明什么

**产出**：更新 `docs/02-architecture-overview.md` 和 `docs/08-api-contract.md`。

**验收标准**：用户（也就是你）看完之后能说"这就是我想要的样子"，并且能感觉到没有过度设计。

### 边：从大陆 0 到大陆 1

只有当 0.1、0.2、0.3、0.4 都完成后，才能进入大陆 1。0.1 和 0.2 可以并行，0.3 和 0.4 可以部分并行，但 0.4 必须等 0.1-0.3 的输入。

## 3. 大陆 1：前端视觉与交互骨架

这块大陆的目标是：让 Iris 有一个能跑起来的、视觉上达到 WonWork 水准的界面。它暂时不需要真的能调用后端，只需要能显示数据、能交互、有动画。

### 节点 1.1：设计令牌系统

**目标**：建立 Iris 的视觉语言。

要产出：

- Tailwind 配置扩展：颜色、字体、间距、圆角、阴影、动画曲线
- CSS 变量：亮色/暗色主题
- 基础组件：Button、Input、Card、Badge、Modal、Toast

**参考**：WonWork 的视觉风格，但要更明亮、更透气，符合 Iris 彩虹女神的意象。

### 节点 1.2：瀑布流布局骨架

**目标**：实现对话消息的基本瀑布流渲染。

要产出：

- `WaterfallTurn` 组件：一轮对话的容器
- `FlowNode` 组件：消息、思考过程、工具调用、答案、审批条等节点的渲染
- 虚拟滚动：长对话不卡顿
- 过程折叠/展开：用户能看摘要，也能看细节

### 节点 1.3：Composer 与输入系统

**目标**：实现用户输入框和发送逻辑。

要产出：

- 多行输入框、自动增高
- 附件按钮（视觉先占位，功能后实现）
- 权限模式选择（bypass / auto / confirm / sandbox）
- 补充注入的 UI 表达

### 节点 1.4：状态管理骨架

**目标**：让前端有一个可扩展的状态层。

要产出：

- `chatStore`：消息、轮次、renderNodes、流式状态
- `conversationStore`：会话列表、当前会话
- `viewStateStore`：滚动位置、折叠状态、主题

### 节点 1.5：暗色主题与响应式

**目标**：让界面在不同环境下都可用。

### 并行关系

1.1 要先完成，因为它是 1.2、1.3 的输入。1.2 和 1.3 可以并行。1.4 和 1.2/1.3 部分并行。1.5 可以最后做。

### 边：从大陆 1 到大陆 2

验收标准：前端能独立运行，显示模拟的对话数据，瀑布流滚动流畅，主题切换可用。不需要真实后端。

---

## 4. 大陆 2：Agentic 运行内核

这块大陆的目标是：让 Iris 真的能思考、调用工具、管理上下文、持久化历史。

### 节点 2.1：后端 SSE 代理

**目标**：后端能转发模型流式响应到前端。

要产出：

- `/api/chat/proxy` 接口
- 支持 OpenAI/智谱/Anthropic 兼容格式
- API key 只存在于后端

### 节点 2.2：对话历史持久化

**目标**：会话和消息能存进 SQLite。

要产出：

- 会话表、消息表、renderNodes JSON 列
- 创建、读取、更新、列表接口

### 节点 2.3：轮次模型（Round）

**目标**：后端能理解一次完整对话的轮次结构。

要产出：

- Round 状态机：user → thinking → tool_calls → tool_results → assistant
- 工具调用解析：从模型响应中提取 tool_use
- 工具结果回注：把结果拼回上下文

### 节点 2.4：上下文管理

**目标**：长对话不会爆上下文。

要产出：

- token 估算
- 压缩线（CompactBoundary）
- 窗口裁剪策略
- 长对话错误处理（prompt too large 等）

### 节点 2.5：工具执行框架

**目标**：后端能执行工具并返回结果。

要产出：

- Tool 接口/抽象类
- ToolRegistry
- 同步/异步执行器
- 结果统一封装

### 节点 2.6：前端与后端对接

**目标**：前端能接收 SSE 事件并更新 UI。

要产出：

- SSE 事件类型定义：token、tool_start、tool_done、approval_request、error、done
- 前端事件解析器
- renderNodes 实时更新

### 并行关系

2.1 和 2.2 可以并行。2.3 依赖 2.1 和 2.5。2.4 依赖 2.3。2.6 依赖 2.1 和 1.4。

### 边：从大陆 2 到大陆 3

验收标准：完整走通一次"用户提问 → 模型思考 → 调用工具 → 返回结果 → 生成答案"的流程，刷新页面后历史还在。

---

## 5. 大陆 3：工具平台与能力目录

这块大陆的目标是：让 Iris 拥有可扩展的能力网络。

### 节点 3.1：Tool 契约与 Registry

**目标**：定义一个 Tool 必须是什么。

要产出：

- Tool 接口：name、description、path、riskLevel、parameters、execute
- ToolRegistry：注册、发现、按路径查找

### 节点 3.2：能力目录服务

**目标**：让模型能按目录导航工具。

要产出：

- `/api/tools/capabilities/tree`
- `/api/tools/capabilities/search`
- `/api/tools/schema`
- 目录统计：每个节点下有多少工具

### 节点 3.3：审批闸门

**目标**：写操作必须被批准。

要产出：

- ApprovalGate
- 审批状态机
- SSE 审批事件
- 前端审批条

### 节点 3.4：工作区服务

**目标**：文件操作安全可控。

要产出：

- WorkspaceService.resolve() 路径围栏
- 检查点机制
- 文件读写工具

### 节点 3.5：Python 沙箱

**目标**：能运行 Python 处理数据。

要产出：

- 子进程执行器
- 超时控制
- 输出截断
- 产物卡片

### 节点 3.6：首批生活工具

**目标**：让 Iris 有真实可用能力。

要产出：30+ 个工具，覆盖 notes、finance、calendar、files、job、travel 等领域。

### 并行关系

3.1 必须最先完成。3.2、3.3、3.4 可以并行。3.5 依赖 3.4。3.6 依赖 3.1-3.5。

### 边：从大陆 3 到大陆 4

验收标准：模型能通过目录找到陌生工具并正确调用；写操作必审批；Python 沙箱能生成一份报告。

## 6. 大陆 4：WebBridge 浏览器自动化

这块大陆的目标是：让 Iris 能操作网页。

### 节点 4.1：守护进程

**目标**：启动一个能控制 Chrome 的进程。

要产出：

- Node.js CDP 或 Java Playwright 守护进程
- 本地 HTTP 通信
- 认证机制

### 节点 4.2：页面状态原语

**目标**：Iris 能"看见"网页。

要产出：

- DOM 快照
- 可见元素列表
- 表单字段识别
- 截图

### 节点 4.3：动作原语

**目标**：Iris 能操作网页。

要产出：

- 点击、输入、滚动、选择、提交、等待
- 动作序列执行

### 节点 4.4：借窗模式与接管

**目标**：人能随时接管。

要产出：

- attach 到用户已有 Chrome
- 人工接管按钮
- 状态同步

### 节点 4.5：录制回放

**目标**：一次示范，多次重放。

要产出：

- 动作录制器
- 工作流格式
- 回放引擎

### 并行关系

4.1 最先。4.2 和 4.3 可以并行。4.4 依赖 4.1-4.3。4.5 依赖 4.4。

### 边：从大陆 4 到大陆 5

验收标准：能完成一次真实网申填表流程，并在提交前停下来等你确认。

## 7. 大陆 5：产品化与稳定

这块大陆的目标是：把 Iris 变成可安装、可更新、可信赖的产品。

### 节点 5.1：后端打包

**目标**：后端能独立运行。

要产出：

- Spring Boot 可执行 jar
- 内嵌前端静态资源
- 内嵌 SQLite

### 节点 5.2：构建脚本

**目标**：一条命令构建完整产品。

要产出：

- PowerShell 构建脚本
- dev / prod / external 通道
- 构建期检查（编译、类型、基础冒烟）

### 节点 5.3：安装器

**目标**：用户能一键安装。

要产出：

- Inno Setup 脚本
- 快捷方式
- 卸载程序

### 节点 5.4：启动器

**目标**：双击图标就能用。

要产出：

- 检测 Java 环境
- 启动后端
- 打开前端窗口
- 守护进程管理

### 节点 5.5：更新机制

**目标**：能推送新版本。

要产出：

- version.json
- 版本检查
- 增量更新或全量更新

### 节点 5.6：稳定与可观测

**目标**：产品不轻易崩溃。

要产出：

- 结构化日志
- 错误上报（本地文件，可选关闭）
- 性能监控
- 崩溃恢复

### 并行关系

5.1、5.2、5.3 可以并行。5.4 依赖 5.1。5.5 依赖 5.2。5.6 贯穿始终。

## 8. 条件边与人类确认点

图中有几处必须停下来等用户确认：

1. **大陆 0 完成后**：确认架构设计，再进入实现。
2. **大陆 1 完成后**：确认前端视觉方向，再进入后端开发。
3. **大陆 2 完成后**：确认 Agent Loop 稳定，再扩展工具平台。
4. **大陆 3 完成后**：确认工具平台足够健壮，再进入 WebBridge。
5. **每个大陆内部的重大决策**：例如 Loop 放后端还是前端、用什么数据库、用 CDP 还是 Playwright。

这些是人类节点。不要让 Codex 替你做大决定。

## 9. 状态对象

每个节点完成后，更新 `.codex/state.json`：

```json
{
  "continent": "大陆 1",
  "node": "1.2 瀑布流布局骨架",
  "status": "done",
  "outputs": [
    "frontend/src/components/Chat/WaterfallTurn.tsx",
    "frontend/src/components/Chat/FlowNode.tsx"
  ],
  "verification": "npm run build 通过，1000 条模拟消息滚动流畅",
  "next": ["1.3 Composer", "1.4 状态管理骨架"],
  "notes": "..."
}
```

状态让进度可见，让中断后可恢复。

## 10. 给 Codex 的执行节奏

不要一次性把整个 Graph 扔给 Codex。每次只让它完成一个节点，最多一个大陆。

每次启动时，说：

> "我们现在在大陆 X，节点 Y。请阅读相关文档和参考源码，先输出你的实现方案，等我说'执行'后再写代码。完成后运行验证命令，并更新 .codex/state.json。"

如果 Codex 试图跳过学习直接写代码，制止它。如果它试图复制外部文件，制止它。如果它做出的设计你不认可，停下来讨论。

前期重设计，中期重实现与选型，后期重稳定与拓展。不要在前期的节点里过度测试，先让骨架跑起来；但也不要在前期欠下太多技术债，否则后期还不起。

---

## 11. 最终要到达的阶段性效果

走完这六块大陆后，Iris 应该达到这样的状态：

- 打开是一个明亮、流畅、有个人气质的对话界面
- 用户说话，Iris 能思考、能调用工具、能生成答案
- 长对话稳定，不会莫名其妙崩溃或遗忘上下文
- 有一批生活工具可用：记账、记笔记、查快递、整理文件
- 能操作本地文件，所有写操作先问一句
- 能驱动浏览器完成半自动化任务，提交前停下来确认
- 能打包成 exe，在干净 Windows 上安装运行
- 代码结构清晰，新增一个工具只需要写一个类

这就是 WonWork 的水准，甚至更好：因为 Loop 在后端，因为视觉更个人化，因为没有企业业务的包袱，因为一切都是为一个人服务的。
