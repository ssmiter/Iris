# 24 · 丝滑交互体验引擎

> 机制已经 WonWork 跨项目移植验证，新增前提与发散方向见 §15
>
> 依赖：`docs/07-frontend-architecture.md`、`docs/08-api-contract.md`、`docs/11-design-system.md`、`docs/23-runtime-projections.md`
>
> 参考证据：WonWork SVN r188 源码审计（`MessageList` / `WaterfallTurn` / `useTextReveal` / `index.css`）。只吸收已被真实运行验证的机制，不复制实现；本文全部机制以前端投影与 SSE 事实为唯一输入。

## 1. 定义

丝滑不是动画多，而是两条性质：

1. **数据节拍与视觉时钟解耦**——数据以脉冲到达，画面以连续时间呈现；
2. **每次事实迁移都有一段看得懂的过渡**——出生有来路，变化有轨迹，退场有去向。

凡是做不到这两条的"流畅"都是粉饰：要么是把数据脉冲直接拍在屏幕上（逐 token 抖动），要么是发明没有事实出处的动效（装饰）。本文定义的机制全部可测量、可验收。

```text
SQLite 事实 → SSE 事件（后端 64字符/50ms 合并）
           → chatStore（帧级合并提交）
           → 视觉时钟（速率自适应揭示）
           → DOM（过渡白名单内的一切运动）
```

四层各有节拍，互不拖累：后端合并保写放大，store 合并保 React，视觉时钟保连续感，过渡白名单保注意力。

### 1.1 三条水位线

实现时不能只问“接口是不是流式”，而要同时观察三条独立水位：

| 水位 | 含义 | 权威来源 |
|---|---|---|
| 事实水位 `fact frontier` | 模型已经产生并被系统接受到哪里 | provider stream / SQLite / SSE |
| 投影水位 `projection frontier` | 当前会话视图已经能定位并选择哪些事实 | render node、Round 链接、store selector |
| 视觉水位 `visual frontier` | 用户此刻实际看到了哪里 | reveal engine |

必须始终满足：

```text
visual frontier ≤ projection frontier ≤ fact frontier
```

视觉可以有界落后，但不能越过事实；投影不能因为正式关系尚未最终落定而隐藏
已经存在的流式事实。三条水位混在一起时，常见结果有两种：直接把事实脉冲拍到
屏幕上，或数据已经流式到达但画面直到完成才整块出现。

### 1.2 “流式”是端到端性质

以下任一项成立，用户看到的都不是流式：

1. provider 只在完成时返回全文；
2. 后端产生 delta，但 SSE 缓冲到最后才发送；
3. store 收到 delta，但目标节点尚未进入当前视图投影；
4. 组件直接渲染脉冲式权威全文，没有视觉时钟；
5. `completed` 事件到达时强制跳过尚未展示的视觉尾巴。

因此排查顺序必须从事实、投影到视觉逐层推进，不能先调动画时长。

## 2. 视觉时钟：揭示引擎

流式文本的"自然生长"由一台独立引擎驱动，组件不直接渲染 store 里的最新文本。

### 2.1 机制

- 全局共享 rAF ticker：所有活跃揭示句柄挂在同一表上，无句柄时自动停表；
  单帧 `dt` 封顶 100ms，切 tab 回来后不大跳；
- 到达速率估算：对最近 5 次 `setTarget` 做 EMA，得到数据到达速率；
- 揭示速率 = 到达速率 × 1.25，钳制在 `[40, 600]` 字符/秒——略快于到达，
  保证落后不超过一个小窗口，又不会一瞬吐完；
- 首帧快进：重新挂载一个**已经推进中的活跃流**时，可直接揭示到尾部前
  24 字符，只给最后一小段留动画，避免虚拟列表重挂载后从头打字；新鲜创建且
  从第一批开始可见的答案不把整段历史误当作首帧补偿；
- 文本变短（invalidated / 重置）→ frontier 归零，按退场规则处理（§3.3）；
- `prefers-reduced-motion`：跳过引擎，即时全量呈现。

### 2.2 两种模式

| 模式 | 用于 | 行为 |
|---|---|---|
| `chars` | 最终答案、阶段答案正文 | 按字符前沿推进 |
| `blocks` | 结构化块（表格、清单、代码） | 按块推进，块内一次性呈现 |

### 2.3 与 store 的关系

引擎不是第二份状态。store 中的 `AnswerNode.content` 永远保存最新权威文本
（帧级合并后）；引擎只持有 frontier 与速率两个标量，输出"当前应显示的前缀"。
组件渲染引擎输出，不渲染 store 原文——但任何时候刷新、重连、切分支，
水合数据直接全量呈现，不经过引擎。

### 2.4 完成不是视觉中断

`completed` 只表示事实不再增长，不表示视觉前沿必须瞬移到事实前沿：

- 若视觉已追平，立即移除光标并提升为终态；
- 若仍有尾巴，冻结 target、继续揭示，追平后再提升；
- 用户切分支、刷新或恢复历史得到的 completed 节点直接完整显示，不重放；
- `prefers-reduced-motion` 始终立即追平。

这一区分让“实时发生的完成”与“历史事实的水合”拥有不同的视图语义，同时不
发明新的业务状态。

## 3. 流式正文渲染

### 3.0 先让节点进入视野

视觉引擎只能平滑已经被组件选中的节点。Iris 的 streaming answer 在第一批文本
时即成为持久化 render node，但正式 `round.answerNodeId` 原先要到 attempt 完成
时才写入。若前端只信该正式链接，整个流式节点会存在于 store 中却不在 DOM 中，
最终只能在完成或重新水合后整块出现。

当前采用两阶段选择：

```text
正式链接存在
  → 使用 round.answerNodeId 指向的节点
正式链接尚未落定
  → 使用明确声明 node.roundId == round.roundId 的 answer 节点
```

`roundId` 是节点自身的持久化事实，不是根据数组位置、相邻节点或时间猜测；
正式链接一旦存在就拥有更高优先级。这个“视觉桥梁”只补齐投影可见性，不修改
后端事实，也不把临时选择伪装成最终领域关系。

### 3.1 三段呈现

1. **已揭示前缀**：按增量 Markdown 排版，已闭合块（段落、代码围栏、表格）
   绝不重排重解析；
2. **尾部窗口**：揭示前沿之后最多一屏字符，以逐字淡入过渡（`opacity` .38s，
   交错延迟封顶），超出窗口的未到达数据不产生任何 DOM；
3. **未闭合块**：代码围栏、表格、引用未闭合时按纯文本容错呈现，不反复解析
   全文 AST。

不做全量逐字 `<span>`，不设字符数硬上限：已揭示前缀是普通排版文本节点，
只有尾部窗口产生少量过渡元素，长答案的 DOM 成本与流式无关。

### 3.2 完成提升

`render_node.updated(completed)` 到达后先冻结权威 target；视觉尾巴尚未追平时
继续使用同一容器揭示，追平后从容错排版一次性提升为完整 Markdown。流式容器与
终态容器共用相同的字体、行高与宽度约束，提升零位移；提升不重触揭示动画。

### 3.3 失效退场

`render_node.invalidated` 到达：

- 已显示内容原地淡出（不瞬间清空用户已读文字）；
- 原位呈现 FailureView 的人话原因与恢复入口（重试/重新准备/澄清）；
- 重试产生新 attempt 时，同一节点身份下重新开始揭示。

### 3.4 光标

流式期间答案末尾显示一条 2px `text-subtle` 竖线，1.4s 低频明暗；
`completed` 即消失。全文唯一，不随节点复制。

## 4. 滚动跟随

只有 `following` / `reviewing` 两态，不存在第三种隐藏策略：

- **意图识别只信原生输入事件**：`wheel deltaY < 0`、`PageUp / ArrowUp / Home`、
  触屏下拉超过 8px → `reviewing`；程序化滚动不触发这些事件，永不误判；
- **回到底部**（80px 容差内）→ `following`；
- `reviewing` 期间按 **Turn 粒度**累计"新增 N 轮"，不随字符流跳数字；
- "回到最新"胶囊平滑滚动恢复跟随；
- 展开历史 Round、审批退场、补充落入：视口锚点不动。

## 5. 折叠与展开

- 高度动画只用 `grid-template-rows: 0fr ↔ 1fr` 纯 CSS 过渡
  （.4s `cubic-bezier(.4,0,.2,1)`），不用 JS 测高；
- 摘要行位于过程区**下方**，是永久视觉锚点：展开时内容从锚点上方撑开，
  锚点随之下滑，眼睛零寻找；
- 折叠状态纯手动：只有用户点击修改；token delta、节点完成、Round 切换、
  Turn 终态、虚拟列表重挂载均不得改写；状态存 `viewStateStore`；
- Round 的默认粒度是摘要。用户首次展开 Round 时，同一状态提交把其中尚未
  见过的 Node 详情全部展开；此后用户单独收起某个 Node 的选择被保留，
  关闭再打开 Round 不覆盖。展开期间新到达的 Node 以详细粒度进入；
- “全部展开/收起”是批量视图操作，不触碰业务数据。

## 6. 出生、脊柱与终态过渡

- 节点出生：`.42s` 淡入 + 6px 上浮；来路脊柱段 `scaleY(0→1)` `.5s` 生长；
- 脊柱流动有因果序：只有前序节点进入终态，通向下一个节点的脊柱段才生长；
- 已终态 Turn（含刷新水合、切分支恢复）**不重放**任何出生动画——
  出生只表达"刚刚发生"，不表达"历史上发生过"；
- Turn 终态事件到达后进入约 300ms 视图过渡期：流动元素定格、脉冲收敛，
  随后进入 settled。过渡期是纯视图状态，由 `run.settled` 事件驱动，
  不由组件计时器发明业务阶段。

## 7. 审批的两阶段退场

- 决定（批准/拒绝）→ 该条转为 ghost：**原位淡化 500ms**（布局完全不动，
  其余条目不补位）→ **收拢 350ms**，余项此时平滑上移；
- 顺序稳定：按首次出现位置排列，新审批追加在最靠近 composer 一侧；
  ghost 保持原槽位直至移除；
- 防重：决定提交期间该条进入 busy，重复点击不产生第二次决议；
- 整条主操作 = 批准，拒绝为清晰的次级操作；`Tab` 快速批准首项
  （模态语义，window capture 阶段拦截，IME 组合与输入框内不生效）；
- 本地只表达"决议已提交"；最终状态以 `attention.updated` 为准，
  决议与后端冲突时以后端事件收敛，不回放本地假象；
- 浮动条经 Portal 挂载，避免祖先 `overflow/transform` 裁剪；
- Round 内审批卡与 composer 上方浮动条是同一 `attentionId` 的两个 selector，
  共享同一份事实。

## 8. 点击三阶段

每次点击都走同一条路径，无一例外：

```text
按压反馈（90ms，transform/opacity）
  → 提交中（明确的本地等待态：busy、禁用、文案不夸大）
  → 事实事件收敛（turn.accepted / attention.updated / supplement.updated …）
```

三阶段之间无跳变、无闪烁、无双重确认。提交中不伪造结果；事实到达前的
一切视觉都只是"你的动作被接住了"，不是"事情已经发生"。

## 9. 补充的视觉生命周期

```text
submitting → pending → injected | cancelled | promoted
```

- `submitting / pending`：composer 上方 chip，文案"待送入"，可撤回；
- `injected`：chip 原位确认淡出；同时在 `injectedAfterRoundId` 指定的 Round
  边界落为一条普通用户气泡——视觉上与最初提问同层，位置是后端事实，
  前端不看相邻节点猜；
- `promoted`：chip 转为排队的新 Turn，不伪称已注入；
- `cancelled`：chip 直接退场；
- Turn 停止时未注入文本保留在草稿区，绝不自动再次执行。

## 10. 颜色与状态纪律

- 正文全程只使用 `text` 系令牌：禁止渐变、闪烁、逐字变色、呼吸高亮；
  流式生长的唯一"活"是文本追加本身；
- 状态表达 = 语义色 + 图标 + 文字三者取二；彩色脉冲只允许出现在运行锚点
  （缎带脉冲点 / 活跃节点 halo）一处一时刻；
- 彩虹光谱只属于品牌身份与当前活动锚点（11 §2.3），正文与过程区永远中性；
- 用户阅读最终答案时，视野内没有任何元素在动、在闪、在变色。

```text

│   ├── revealEngine.ts        # 共享 ticker + 速率估算 + frontier

│   └── transitions.ts         # 揭示阈值与过渡白名单常量

│   ├── AnswerBlock.tsx        # 当前 chars 揭示与完成提升

│   ├── useConversationFollow.ts # 滚动所有权：位置/意图分离、手势打断
│   ├── PendingApprovalStack.tsx # 审批浮动条与 ghost 两阶段退场
```

## 12. 验收门槛

每条可演示、可复测：

- 后端 1.2s 一批的脉冲数据，画面呈现连续生长，无批次感；
- 活跃 Turn 每秒 20 次 delta 时 Composer 输入无延迟感；
- 首帧长文本不从头打字（快进至尾部前 24 字符）；
- 完成提升零位移；失效退场不清空已读内容；
- 审批决定后 500ms 内布局纹丝不动，收拢时余项平滑补位；
- 展开历史 Round、切分支、刷新水合：锚点不动，出生动画不重放；
- reviewing 期间任何流式内容不抢视口，"新增 N 轮"按 Turn 计数；
- 1000 个已完成 Turn 滚动无可见掉帧；
- 阅读最终答案时视野内无运动元素（运行锚点除外）；
- `prefers-reduced-motion` 下揭示引擎与全部过渡即时完成。

### 12.1 诊断观测点

开发模式应能按 node 关联以下时间点；默认不进入用户日志：

```text
t0 provider fragment
t1 render_node.added / delta 持久化
t2 SSE 到达浏览器
t3 store 帧提交
t4 节点首次进入 DOM
t5 visual frontier 推进
t6 completed 到达
t7 visual frontier 追平
```

判断原则：

- `t2 - t1` 大：事件输送或代理缓冲问题；
- 有 `t3`、无 `t4`：投影选择/父级链接问题；
- 有 `t4`、`t5` 与 `t3` 同步跳跃：视觉时钟没有真正接管；
- `t5 < t6` 但 `t7 == t6`：完成事件截断了视觉尾巴；
- 输入卡顿但上述延迟正常：Markdown 解析或 React 提交成本过高。

## 13. 当前实现切片

第一轮已落地的是影响主观丝滑度最大的纵向链路：

- `chatStore` 对高频 `render_node.delta` 逐帧合并，版本链仍按事件顺序验证；
- streaming answer 在正式 `round.answerNodeId` 链接落定前，依据节点自身持久化的
  `roundId` 挂入对应 Round；完成后由正式链接自然接管，避免流式节点存在却不可见；
- `motion/revealEngine.ts` 以共享视觉时钟维护展示前沿，限制后台恢复时的
  时间步长，并依据到达速率平滑追赶；
- `AnswerBlock` 在流式阶段使用展示前沿，完成、水合与
  `prefers-reduced-motion` 场景直接提升为权威全文；完成事件先到时不截断
  尚未展示的视觉尾巴，尾巴追平后再无位移提升；历史水合不重放；
- 揭示发布只停在完整 grapheme cluster 边界；扫描从上次已显示边界继续，
  不在每帧重切全文。完成事件先到但视觉未追平时，光标与 `aria-busy`
  继续服从视觉水位，追平后才结束；
- `IncrementalMarkdown` 只让仍在生长的尾部参与重复解析；围栏外已经闭合的
  顶层块被冻结为 memoized fragment，后续字符增长不再重解析历史块。代码围栏、
  连续引用与跨空行列表保持在同一未冻结片段，避免为了缓存破坏 Markdown 语义；
- `ConversationTimeline` 只把滚轮上行、向上键与触摸回看识别为 reviewing，
  流式增长本身不再误触发脱离跟随，新增提示按 Turn 计数；
- 对话正文、过程、侧栏与顶部栏移除非必要卡片边界；Composer 作为主操作面
  保留单一轻边界，并以画布渐隐承接内容。

第二轮（2026-07-30，WonWork 瀑布流视觉经验回迁）已落地：

- 脊柱水流感：已到达段 `primary/15` 染色在活跃节点呼吸点收束成"水流前沿"，
  失败节点 `danger/20`；首节点短桩、末节点渐隐收尾，链条两端不再悬空；
- 节点出生：来路线段 `scaleY` 生长 + 内容淡入微升（280ms `ease-enter`），
  仅"回合活跃 + 过程区可见 + 挂载瞬间"触发；模块级快照集合防虚拟列表
  重放，水合与 settled 零动画（§6）；
- 活跃节点 halo 光环（attention 等待态 warning 色、更急促），思考节点
  完成时展示后端已喂的 `durationMs`；
- 长内容软截断 `ClampText`（阈值 168px + 24 余量，底部渐隐 + 展开全部）；
- 审批 ghost 两阶段退场完整版：`PendingApprovalStack` 浮动条（composer

## 14. 本轮故障的结论

本轮最初现象是：短消息和长消息都像在完成时突然整块出现。初看容易归因于
揭示速率过快或消息太短，但代码链路给出了不同答案：

1. OpenAI-compatible provider 已以流方式输出；
2. `AnswerStreamProjector` 已按 64 字符 / 50ms 阈值创建和更新 answer node；
3. SSE 与 `chatStore` 已能接收 `render_node.added / delta`；
4. 但 Round 只渲染 `round.answerNodeId`，该正式链接在完成前为空；
5. 所以 visual frontier 实际上根本没有起跑，而不是跑得太快。

由此得到三条长期结论：

- **先证明节点可见，再优化节点如何运动。**
- **领域关系的最终确定时间，不应无意中成为实时视图的可见时间。**
- **视觉桥梁必须建立在明确元数据上，并让位于最终权威链接；绝不依赖 UI
  邻接关系猜测。**

这也是 Iris 所谓“原生丝滑”的含义：从 provider、持久化事件、投影选择、
React 提交一直贯通到用户眼睛，而不是在最上层补一个打字机效果。

## 15. 跨项目实践：WonWork 移植（2026-07-26）

WonWork 与 Iris 同宗，但 agentic 内核在前端（TS）、数据节拍由前端
renderScheduler 自定。将本文机制整体移植后，流式顿挫（"一块一块、像卡住"）
消除。实践同时验证了机制的可移植性，也暴露了本文此前未写明的前提条件。

### 15.1 移植验证了什么

- **三水位排查法可复用**：在另一条技术链（无 SSE、无后端投影器）上，
  按事实 → 投影 → 视觉逐层推进，同样一次定位到根因链，且根因分布在
  每一层：数据节拍 1.2s 脉冲（投影层）、揭示策略缺陷（视觉层）、
  隐藏截断与换脸（渲染层）、重渲染范围过大（React 层）。
- **RevealController 可整体搬运**：约 190 行、零框架依赖（仅用 rAF 与
  Set），EMA、积压快进、settleTarget、发布节流全部按原参数生效。
- **流式即排版可消除完成跳变**：对已揭示前缀直接渲染 Markdown、
  终态共用同一容器与排版约束后，"完成"在视觉上不再是一个事件。

### 15.2 本文此前未写明的前提

- **节拍密度是 ×1.25 追赶策略的成立条件**。揭示速率 = 到达速率 ×1.25
  隐含假设批次间隔远小于批次揭示时间（Iris 后端 50ms 一批天然满足）。
  WonWork 原节拍 1.2s 一批时，每批 0.96s 吐完后干等下一拍，顿挫感
  正是由此产生——此时正确策略不是调倍率，而是先把数据节拍细化
  （100ms / 48 字），让追赶策略重新成立。**节拍与揭示速率是联合设计，
  不能独立调参。**
- **隐藏截断是卡顿的隐形来源**。WonWork 流式渲染存在 1000 字硬 cap
  （`slice(0, 1000)`），长答案中途画面冻结直到完成整块弹出。这属于
  §14"先证明节点可见"的推论：不仅要证明节点出现，还要证明
  **visual frontier 在整个流式期间持续可达 fact frontier**，任何
  "临时上限"都会在中途制造一堵看不见的墙。
- **零位移的关键是容器约束，不是动画参数**。流式与终态不换脸依赖
  两者共用字号/行高/宽度约束；只要排版约束一致，提升甚至不需要
  任何过渡动画。
- **变密 flush 的成本要先证伪再实施**：WonWork 把 flush 加密 12 倍
  之前，先核实了投影是增量的（drainOps）、提交是纯内存 set
  （持久化与渲染节拍无关）。加密节拍是安全的当且仅当这两个性质成立。

### 15.3 可进一步探索的方向（发散）

本小节主题后续值得收敛的方向，按层次列出，供以后选题：

- **增量 Markdown（第一切片已实现）**：Iris 已把围栏外的安全闭合块冻结为
  memoized fragment，只有未闭合尾部重复解析；这消除了普通长文的全文重解析。
  后续仍需用真正的块级 AST 缓存覆盖复杂嵌套列表、自定义容器和超长单一代码块。
- **字素级揭示（第一切片已实现）**：frontier 的速率仍按 UTF-16 长度估算，
  但发布位置通过 `Intl.Segmenter` 吸附到完整 grapheme cluster 边界；
  扫描从上次可见边界增量继续，并只读取 64 code units 前视窗口。后续若要让
  速率本身也按字素计量，再单独评估中英文、emoji 混排下的体感与成本。
- **节拍-速率联合自适应**：scheduler 观测真实到达速率后反向调节自身
  节拍——慢模型加密节拍（保连续感），快模型放宽节拍（保写放大），
  让"数据脉冲密度"始终落在揭示引擎 ×1.25 策略成立的区间内。
- **诊断观测点落地**：§12.1 的 t0–t7 时间戳目前仍是纸面定义，两个
  项目都未实现；一个开发模式的 per-node 延迟面板能把"感觉卡"
  变成可定位的水位数据。
- **揭示引擎的形态扩展**：chars 之外，结构化块（表格/代码/清单）按
  块揭示（blocks 模式在两项目均未真正实现）；语音朗读、翻译等
  下游消费方也可以订阅 frontier 而非全文。
- **WonWork 侧尚未对齐的本文机制**：滚动跟随两态意图识别（§4）、
  审批 ghost 两阶段退场（§7）、千 Turn 长列表性能校准（§12）、
  完成过渡期 settled 语义（§6）。这些可作为下一轮移植清单。
- **跨项目共享封装**：RevealController 已被证明无项目耦合，抽成
  独立包（输入文本 + 事件回调，输出前缀快照）可避免两份实现
  各自漂移；transitions 常量同理。

## 16. 对话视口所有权（2026-07-30）

前端进入正式打磨期后，滚动不再被视为一个组件参数，而是一项明确的用户
所有权。参考 WonWork 最新产品实现与 v6/v8/v9 原型的取舍，Iris 收敛为：

- **虚拟列表是唯一滚动所有者**。正文、过程节点、揭示引擎和 Composer
  都不得直接改写 `scrollTop`；它们只改变内容高度，由列表统一承接。
- **位置与意图分离**。`atBottom` 只是几何事实，`following/reviewing`
  才代表用户意图。`followOutput` 必须同时满足“仍在 following”与
  “列表更新前确实位于底部”，不能仅凭 store 中的旧状态强制回底。
- **全部原生阅读手势都可打断跟随**。除向上滚轮、键盘、触摸外，还包括
  滚动条拖动、轨道点击和按住指针产生的滚动；程序化跟随不伪装成用户意图。
- **同一 Turn 内的高度增长也属于流式输出**。最后一项的 Markdown 揭示、
  工具节点出生和状态文案变化会改变列表总高；following 时按帧合并并追随
  新底部，reviewing 时不改视口。
- **展开权属于用户**。Round 默认闭合；用户展开后，内部尚未见过的 Node
  默认展示详情，随后每个层级都可独立收起。SSE delta、完成事件、虚拟列表
  重挂载均不得覆盖已经表达过的选择。reviewing 中展开过程时，后续流式
  高度变化不得把点击位置抢走。
- **回到最新是唯一显式恢复入口之一**。用户自然滚回底部或点击胶囊后恢复
  following；恢复只做一次定位，随后由内容自然增长把已有内容向上推。
- **几何稳定优先于动画**。正文列、Composer 使用同一宽度 token，滚动条
  预留稳定槽；折叠使用文档流内的 `grid-template-rows`，不测量高度、不做
  绝对定位补偿。动画只能解释已经发生的状态变化，不能参与布局决策。

这一轮的验收重点不是“有自动滚动”，而是：用户不操作时最新内容始终自然
可见；用户一旦开始阅读历史，页面就完全安静；展开、流式增长和回到底部三者
无论怎样交错，都不产生回弹、抢焦点或自动闭合。
