# 01 · 产品哲学与面向业务的设计思考

> 当前定位：Iris 首先是一套吸收工业互联网项目经验、面向产品级 Agent 的本地运行
> 内核。个人助手是重要的产品方向，但不是现阶段用来预定义大量生活能力的理由。
> 当前只建设已经能被 reference 和真实运行验证的基础：Loop、上下文、工具、审批、
> 恢复、工作区与可观测投影。工业场景或个人场景都是后续验证这套地基的业务载荷。

## 1. 从一个判断说起

> 这个时代的瓶颈已经不是"AI 能不能做"，而是"人把需求讲清楚、把过程看住、把结果接住"的成本。
> 文档足够清晰时，实现是顺其自然的。产品亦然：把**人如何交代任务、如何监督过程、如何验收结果**设计好，能力会自己长出来。

Iris 的所有设计都围绕这三件事：

| 环节 | 问题 | Iris 的答案 |
|---|---|---|
| 交代任务 | 一次说不清，过程中想补充 | 运行中补充注入 + 排队消息（不打断，下一个边界送达） |
| 监督过程 | 黑盒等待焦虑，细节又太吵 | 瀑布流：过程折叠为摘要行，想看一眼展开，答案逐字揭示 |
| 验收结果 | 出错回不去，危险动作心慌 | 分支多叉树（任意位置分叉重来）+ 审批条（写操作先问一句） |

## 2. 工具的隐喻：从工业经验到通用 Agent 地基

Iris 前期先建设可靠的 Agentic 求解器，因为能力发现、组合和缺口修复都依赖它。
现阶段不急于判断最终产品一定属于个人生活还是工业互联网，也不通过罗列未来场景证明
平台价值。先把 reference 已经暴露出的共同难题做深：模型协议、运行恢复、工具契约、
能力发现、写操作审批、上下文预算和前后端状态投影。

大规模工具平台的灵感来自制造业 MES：一个工厂有几百上千个“工序”，每个工序是一个
结构化操作。这个经验先抽象成 Agent 基础设施，而不是立即平移成生活工具清单：

| 工业项目经验 | Agent 基础抽象 |
|---|---|
| 工序（查/改/录） | 语义客观、输入输出明确的 Tool |
| 车间 / 产线 | 可发现的 Capability domain / catalog |
| 工艺路径 | 可版本化、可验证的 Pipeline |
| 作业指导书 | description + schema + 前置条件 + evidence |
| 生产审批 | snapshot-bound Approval + Commit Gate |
| 批次追溯 | Run/Round/Event、检查点与恢复事实 |

关键洞察：**工具数量会膨胀，但人类和模型的当前注意力都不会膨胀**。目录树让能力可组织，却不能单独解决几千个能力的版本、可用性、召回和上下文驻留。Iris 还需要可搜索 Catalog、稳定 Capability identity、Definition 生命周期，以及有预算的当前能力视野；Provider 工具表面则保持小而稳定。

## 3. 模型的元认知：先发散，后收敛

面对 1000 个工具，把 schema 全塞进上下文是灾难（贵、慢、还干扰推理）。正确姿势是教人找东西的流程：

```
理解意图 → 看目录顶层（每个目录带工具数统计）
        → 进入最可能的子目录
        → 读少量候选 Manifest，并为当前 Model Step 激活 schema
        → 信息不足就向用户澄清一句
        → 调用
```

配套禁令：不凭工具名猜参数；不调用没读过 schema 的工具；搜索无果先换关键词而不是放弃。

这套流程把"模型会不会用工具"从运气问题变成了工程问题：目录统计给方向感，精确 Definition 按需进入普通动态历史，稳定代理承接真实调用，澄清机制兜住歧义。对话再长、调用再多，曾经读过的 schema 也不会自动永久驻留；完整 ID/version provenance 留在 canonical ToolCall/Exposure/Resolution，压缩只引用事实与少量未来求解 hints，需要时重新发现和读取。

## 4. 对话即界面：视觉不是装饰

终端式交互把信息压成字符流，丢失了大量"位置感"。Iris 认为对话体验的流畅度本身就是生产力：

- **轮次是骨架**：一轮 = 一次发问 + 若干过程 + 一个回答。过程折叠成一行摘要（"思考 3.2s · 调用 4 个工具 · 共 12s"），视线永远先落在答案上。
- **动画只为锚定**：审批条决定后不瞬消——原地淡化半秒再收拢，因为瞬移会让眼睛重新寻找；补充等待时用 chip 确认，进入上下文后在准确位置落为普通用户消息气泡。
- **状态可感知**：压缩进度条（细轨道微光流动）、运行缎带（墨色脉冲点 + 已耗时）、上下文水位（hintbar 右侧百分比）——全部是低饱和的中性色，信息到了，注意力不被抢。

原则一句话：**减少用户的视觉移动，不主动打破专注。**

## 5. 历史是一棵倒着的树

对话不是一条线，是一棵树：任何一条用户消息都可以编辑重发长出分叉；上下文又会被周期性压缩成摘要。两者必须统一建模：

- **压缩线**：每次压缩在历史中画一条线（切点 + 摘要），线前的记录保持原样，线后的对话以摘要为背景。
- **位置语义**：在哪个位置分叉，就用那个位置该用的上下文——压缩线前分叉用原始上下文，线后分叉用该轮压缩后的上下文。多条压缩线共存，分叉点决定落回哪条线。
- **完整快照**：分支变体保存完整的消息结构（含工具调用细节），切换分支无损还原。

这样，"回到三周前那次讨论换一种问法"和"上次压缩之前的那段还能不能接"是同一个问题的两个侧面，都被位置语义干净地回答。

## 6. 浏览器是重要 Connector，不是当前完成度捷径

大量工业和个人流程最终都落在网页中，但“能点击页面”不等于浏览器能力已经可用。
WebBridge 当前只作为未来 Connector 边界保留；在页面观察、动作验证、接管和恢复没有
稳定以前，不用录制 demo 数量替代 Agent 内核完成度：

- **借窗模式**：启动一个真实 Chrome（带用户登录态），模型通过 CDP 观察页面、执行动作；人随时可以把手放回键盘接管。
- **过程即内容**：浏览器画面以"舞台"形式嵌入对话流，模型操作到哪一步、遇到什么阻碍，实时可见。
- **录制与回放**：人示范一遍 → 生成工作流脚本 → 以后一句话重放。

详见 docs/05。

## 7. 面向业务（而非面向 demo）的检查清单

每加一个能力，自问：

1. 它解决的是一个**真实、重复、可验收**的问题吗？
2. 失败了用户能**回到出错前**吗（检查点/分支/撤销）？
3. 危险吗——需要审批吗，影响陈述说人话了吗？
4. 第 1000 个工具加入时，它还**找得到**吗（目录/统计/搜索）？
5. 用户盯着屏幕时，眼睛需要**多余地移动**吗？

五问皆过，才进主干。
